# 상태 카드 — `gil status --json` 을 사람에게 보여주는 법

이 문서는 **에이전트가 읽는 규칙**이다. gil 은 데이터만 내고, 그리는 것은 네가 한다.

## 왜 네가 그리나

gil 에는 뷰어가 있다. 브라우저에 그래프를 그리는 별도 서버다. 그런데 작업 중에 사람이
알고 싶은 것은 대개 세 줄이다 — **지금 어디, 무엇을 재는 중, 내가 나설 자리인가.**
그 세 줄을 보려고 서버를 띄우고 포트를 찾고 창을 두 개 보는 것이 비용이었다.

그리고 이 자리는 고정된 화면보다 네가 낫다. "두 번째랑 세 번째 시도가 뭐가 달랐어?"
같은 질문에 답하는 뷰어는 만들 수 없다. 너는 그냥 답하면 된다.

**뷰어는 없애지 않았다.** 다 끝난 뒤 전체를 훑는 일은 여전히 그래프의 몫이다. 사람이
"전체 보여줘"라고 하면 그때 뷰어를 안내해라(`gil viewer open`).

## 언제 그리나

- 사람이 "지금 어디야", "어떻게 돼가", "뭐 하는 중이야"라고 물을 때
- **스텝을 하나 끝냈을 때** — 묻지 않아도 한 번. 사람이 흐름을 놓치지 않게
- `waiting_for_human` 이 null 이 아닐 때 — 이건 **반드시**
- 세션을 이어받았을 때(handoff 직후)

매 명령마다 그리지 마라. 늘 뜨는 것은 안 읽힌다.

## 무엇을 그리나

`gil status --json` 한 번으로 충분하다. 상황에 따라 셋 중 하나를 고른다.

### 1) 평소 — 세 줄

```
ail-fullstack / three-curves / s7 analyze
재는 중: state 접근이 초과분을 설명하는가
다음: 사이클을 닫거나(success/fail), 형제 가설을 세운다
```

`purpose` 전문·`plan` 전문·`refutes_if` 전문을 그대로 붙이지 마라. 길다. 한 줄로 줄이되
**줄인 티를 내라**(…). 사람이 전문을 원하면 그때 낸다.

### 2) 사람이 나설 자리 — 눈에 띄게

`waiting_for_human` 이 null 이 아니면 그것이 **지금 유일하게 할 일**이다. 다른 것을
먼저 쓰지 마라. 무엇을 기다리는지와 답하는 법을 그대로 전하고, **네 의견도 한 줄 붙여라** —
사람이 판단하려면 재료가 필요하다. 다만 의견과 사실을 섞지 마라.

```
⏳ 사람이 정할 자리입니다
   무엇을: 이 스텝을 승인할지 기각할지
   제 생각: 반증조건 ①은 충족됐고 ②는 못 쟀습니다. 기각이 맞아 보입니다.
   승인: gil approve   /   기각: gil reject --to s1
```

### 3) 사람이 더 물으면 — 그때 파고든다

"왜 그렇게 됐어?", "s5 랑 뭐가 달랐어?" 같은 질문에는 `gil context <chain>/<cycle>` 이나
`gil log` 를 더 불러 답해라. **미리 다 보여주지 마라** — 그게 뷰어가 걸린 병이다.

## kind 마다 카드가 달라진다

같은 데이터라도 **그 순간에만 의미 있는 것**이 다르다. 반증조건은 `hypothesis` 에서는 앞으로
잴 것이고 `analyze` 에서는 이미 지나간 것이다 — 같은 문장을 같은 자리에 두면 사람은 그 차이를
못 읽는다. 그러니 kind 마다 **맨 위에 오는 것**을 바꾼다.

작업 중인 다섯(`define`·`hypothesis`·`verify`·`analyze`·`pending`)은 "지금 뭘 하나"에 답하고,
종결 둘(`success`·`fail`)은 **"이 사이클이 무엇을 남겼나"** 에 답한다. 뒤 둘은 순서가 뒤집힌다 —
다음 한 수가 아니라 **판정 기준과의 대조**가 본문이다.

| kind | 맨 위 | 빼는 것 |
|---|---|---|
| `define` | 무엇을 풀려는가 · 체인 목적과의 거리 | 반증조건(아직 없다) |
| `hypothesis` | **반증조건**(`refutes_if`) · 고정한 설계(`plan`) | 결론(아직 없다) |
| `verify` | 반증조건 + "지금 이걸 재는 중" 표시 | 되돌아갈 후보(판정 전이다) |
| `analyze` | **결론**(`finding`) · 되돌아갈 자리(`rollback_candidates`) | 반증조건 전문 |
| `pending` | **사람이 정할 것**(`waiting_for_human`) · 판정 기준(`criterion`) | 나머지 전부 |
| `success` | **판정 기준과의 대조**(`toward`) · 다음 과녁(`next_design`) | 다음 한 수(닫는 것 하나뿐) |
| `fail` | **왜 죽었나** · 벽의 지도(어디로 물러섰나) · 배운 것 | 다음 과녁 |

`fail` 에서 한 가지 조심할 것: **fail 은 죽음이 아니라 발견이다.** 이 가설이 죽은 것이지
사이클이 죽은 것이 아니다. 카드가 실패를 사과하는 어조로 쓰이면 사람은 되돌리기를 손실로
읽고, 그러면 앞으로만 가려는 압력이 생긴다 — gil 이 막으려는 바로 그것이다.

### 되돌아갈 자리는 "무엇을 잃는가"와 함께

`rollback_candidates` 의 각 항목에는 `discards` 가 있다 — 거기로 되돌리면 버려지는 스텝들.
**번호만 보여주지 마라.** 사람이 고르는 근거는 "s4"가 아니라 "s5~s7 이 버려진다"이다.
연속이면 범위로 접어라(`s5~s7`), 아니면 나열해라.

## 사이클 띠 — `cycle.steps` 를 그리는 법

카드 위에 사이클의 스텝 그래프를 가로 띠로 놓는다. `cycle.steps[]` 의 `{id, kind, parent, back}`
만으로 배치가 결정된다 — **git 을 따로 뒤지지 마라.** 뒤지면 세션마다 다른 그림이 나온다.

### 배치

| | |
|---|---|
| **척추** | 첫 자식이 부모의 줄을 그대로 잇는다. 곧은 가로선 — 꺾임이 없다 |
| **분기** | 둘째 자식부터 아래로. 부모 자리에서 **수직으로 내려간 뒤** 오른쪽으로 꺾는다 |
| **백트랙** | `back` 이 있으면 붉은 점선. **지나온 경로를 되짚는다**(부모 사슬을 거슬러) |
| | 양 끝은 노드 중앙에 맞물린다. 가로 구간은 그 간선의 살짝 위, 세로 구간은 그 오른쪽 |
| **정렬** | 왼쪽 끝에서 시작. 가로 간격은 **가용 폭에 맞춰 계산**한다(남는 공간이 있으면 가운데로 몰린다) |
| **현재 위치** | 색은 그대로 두고 **바깥 링**. 색은 종류를, 링은 위치를 말한다 |

꺾인 선은 곧 분기다 — 분기가 아닌 간선을 꺾으면 없는 갈라짐을 그린 것이 된다.

### 색 — 일곱 kind

정의 회색 · 가설 보라 · 검증 파랑 · 분석 청록 · 사람 대기 앰버 · 산 잎 초록 · **죽은 잎 코랄**.

죽은 잎을 **빨강으로 칠하지 마라.** 빨강은 오류의 색이라 그걸 쓰면 fail 이 잘못으로 읽힌다.
그리고 **크기·모양·선을 차별하지 마라** — 점선도, 빈 동그라미도, 작은 반지름도 안 된다.
죽은 가지로 가는 실선은 산 가지와 똑같다. 차별하면 사람은 되돌리기를 손실로 읽는다.

### 없는 것을 그리지 마라

`back` 이 비었으면 백트랙 선은 없다. 부모 사슬로 대상에 못 닿으면 아예 그리지 마라.
브랜치 **이름**(`…-s4b1`)은 분기가 아니다 — 분기는 `parent` 가 같은 자식이 둘 이상일 때뿐이다.
(실측으로 값을 치렀다: 없는 간선을 지어내고, 있는 간선을 빠뜨리고, 이름을 분기로 읽었다.)

## `define` 카드

| 자리 | 무엇 |
|---|---|
| 머리글 | **kind 를 왼쪽 위에 강하게** — 색 블록. 그 옆에 사이클 › 스텝, 오른쪽 끝에 체인 |
| 띠 | 위 규칙대로 |
| **문제정의** | 이 사이클이 묻는 것을 **물음으로** 한 줄. 바로 아래 원문을 왼쪽 선과 함께 남긴다 |
| **근거** | `cycle.inherit` — 앞 사이클에서 물려받은 것. 왜 하필 이 문제인지가 여기 있다 |
| 버튼 | **승인 / 기각·수정** 둘. 각 버튼 아래 작은 글씨로 **실제로 무슨 일이 일어나는지** |

물음으로 다시 쓰는 것은 **읽기 보조**다. 원문을 반드시 함께 두어라 — 안 두면 지어내서 감춘
것이 된다. gil 에 저장된 문장은 서술문이고, 그것이 기록이다.

버튼 라벨은 일곱 kind 에서 같지만 **뒤에서 도는 명령은 다르다**(define 은 다음 스텝/정정,
pending 만 진짜 `gil approve`·`gil reject`). 그래서 부제를 단다 — 라벨은 통일하되 무엇이
도는지는 숨기지 않는다.

## 그리지 말아야 할 것

- **그래프를 텍스트로 재현하지 마라.** 노드를 나열하고 화살표를 그리면 화면만 길어지고
  아무도 안 읽는다. 전체 조망이 필요하면 뷰어가 그 일을 한다.
- **JSON 을 그대로 붙여넣지 마라.** 사람에게 보여줄 것은 문장이지 데이터가 아니다.
- **없는 것을 채우지 마라.** `chain` 이 null 이면 "체인 밖"이라고 말해라. 그럴듯한 빈칸을
  메우면 화면은 좋아지고 판단은 틀려진다.
- **`next` 를 창작하지 마라.** gil 이 준 것만 옮겨라. 문법이 허용하지 않는 수를 권하면
  사람은 막힌 뒤에야 안다.

## `warnings` 는 삼키지 마라

`warnings` 에 있는 것은 전부 전해라. 특히 이 둘:

- **"gil 밖 커밋이 얹혀 있다"** — 그 변경은 어느 스텝의 것도 아니다. 그 뒤 gil 이 세는
  모든 것이 실제와 갈린다. 사람 눈에는 `git log` 가 멀쩡하니 조용히 갈린다.
- **"뒤처짐"** — 낡은 값이 그 자리에 있어서 조용히 틀리는 경우다.

경고를 요약하면서 없애지 마라. 요약해도 좋은 것과 아닌 것이 있다.

## 형식

호스트가 무엇을 그릴 수 있느냐에 맞춰라. 표를 그릴 수 있으면 표, 아니면 그냥 줄글.
**형식보다 중요한 건 짧음이다.** 열 줄을 넘기면 세 줄로 줄일 방법을 먼저 생각해라.

사람이 쓰는 말로 써라. `falsify_to` 는 "반증되면 돌아갈 자리", `interview: pending` 은
"기준 문서에 대한 답을 기다리는 중"이다. 필드 이름을 그대로 읽지 마라.

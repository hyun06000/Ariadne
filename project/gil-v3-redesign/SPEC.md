# gil v3 명세 — 커밋 그래프 위의 체인·사이클·스텝

**손 시연이 이 명세를 만든다.** 이 문서는 gil v3 코드가 구현할 청사진이다. 폴더도 md 파일도
없다 — 모든 위계는 커밋의 trailer로, 모든 본문은 커밋 로그로.

## 근본 원칙 — 무조건 gil로 모든 흔적을 남긴다 (상현님, 2026-07-23)

**모든 작업의 흔적은 gil 스텝으로 남긴다.** 조사·공부·구현·판단·실험 — 무엇이든 gil의
스텝 커밋으로 기록된다. gil 밖에서 이뤄진 작업(예: 스텝 없이 도구를 돌리거나 조사하는 것)은
흔적이 없어 재현·계보 추적이 끊긴다. 침묵은 관전자에게 멈춤과 구별되지 않는다. **작업하기
전에 그 작업을 담을 스텝이 열려 있어야 하고, 작업의 결과는 그 스텝의 본문·산출물로 남는다.**

## 지원 플랫폼 · 배포 자산 (규범)

gil은 **git만 있으면 되는 정적 단일 바이너리**다(CGO 없음). 릴리스는 아래 **5개 타깃**을
빠짐없이 굽는다 — 이 목록이 단일 진실원이며, `scripts/release-build.sh`·`install.sh`의 플랫폼
감지·아래 항목이 서로 일치해야 한다.

| OS | 아키텍처 | 자산 이름 |
|---|---|---|
| macOS (darwin) | amd64 · arm64 | `gil-darwin-amd64` · `gil-darwin-arm64` |
| Linux | amd64 · arm64 | `gil-linux-amd64` · `gil-linux-arm64` |
| Windows | amd64 | `gil-windows-amd64.exe` |

각 GitHub 릴리스는 위 5개 바이너리 + `install.sh` + `llms.txt` + `SHA256SUMS`(무결성 게이트,
`install.sh`가 필수 검증)로 구성된다. 빌드는 `scripts/release-build.sh <version>`이 재현하며,
버전은 `-ldflags "-X main.gilVersion=<version>"`로 각인된다(`version.go`). Windows 사용자는
PowerShell로 `.exe`를 받고 셸에서 `.\gil.exe`로 호출한다(POSIX의 `gil`/`./gil`에 대응).

## 0. 브랜치 개념 3층 (상현님 확정, 2026-07-23) — git 브랜치에 매핑

gil의 위계 3층은 **git 브랜치**로 표현된다. 이게 v3의 뼈대다.

| gil 층 | git 표현 | 정의 |
|---|---|---|
| **체인** | 브랜치 | 이전 **닫힌 체인의 끝에서 분기**한 git 브랜치. orphan이 아니다 — 대문을 이어받는다. |
| **사이클** | 사이클 가지 | 체인 안에서 분기한 가지. 닫힌 사이클 끝 또는 체인 시작점에서 생성. |
| **스텝** | 스텝 가지 | 사이클 안에서 분기한 가지. 스텝 트리(백트래킹·형제)를 git 가지로 표현. |

### 체인 원칙 (상현님 확정, 2026-07-23 — v2 틀을 뒤집음)

1. **체인은 닫힌 체인의 끝에서만 생성된다** (`gil init`만 예외).
2. **사이클은 닫힌 사이클의 끝, 또는 체인의 시작점에서만 생성된다.**
3. **체인·사이클·스텝의 분기는 모두 git 브랜치로 표현된다.**

- **체인이 orphan이 아닌 이유**: 각 체인은 이전 닫힌 체인의 끝을 이어받는다. 그래야 **대문**
  (리드미 3종·온보딩·존재 기록·프로젝트)이 체인을 넘어 보존된다. `gil init`만이 유일한 예외적
  시작점(orphan으로 구현되나 대문을 심는다).
- **⭐ orphan chain 개념 신설 (상현님, 2026-07-24 — 미구현 메모)**: 위 원칙은 *대문 체인*에
  대한 것이다. 그러나 **버려질 수 있는 실작업**(예: gil로 짓는 뷰어)은 대문·gil소스 뿌리에
  이력이 박히면 곤란하다 — 그래서 `git checkout --orphan`으로 **조상 0의 독립 뿌리**에서
  짓는다(뒤엎기 = `branch -D`, 무손실). 같은 레포이므로 gil 바이너리·`refs/gil/global`(존재·
  기억)·CI에 그대로 접근하고, `git log --branches`로 다른 브랜치의 gil 그래프를 읽어 그린다.
  익으면 `gil chain-merge`로 대문에 병합. **git의 `checkout --orphan`이 이미 이 격리를
  제공하니, gil이 이를 일급 개념(`gil chain --orphan` 등)으로 이어받아야 한다** — 지금은
  손으로 `git checkout --orphan` + 인덱스 비우기로 하고, gil이 이를 감싸는 건 미구현.
  - **닦아낼 거친 점 (2026-07-24 실사용 발견)**: (1) orphan 실작업 브랜치는 `./gil` 래퍼
    같은 *추적 파일*을 잃는다 → gil은 PATH의 설치 바이너리여야 한다(래퍼 삭제로 해소).
    (2) 스텝 없는 새 체인(chain-root만)은 `gil log`가 **빈 출력** — chain-root도 노드로
    보이게 하거나 "이 체인에 아직 스텝 없음"을 알려야 한다(LLM 프롬프트 원칙). `gil handoff`는
    이미 chain-root 트레일러로 체인을 감지하니 이 갭은 `gil log` 국소.
- **체인 간 관계**: 필요하면 **머지**로 잇는다(Gil-Merge → 두 조상 상속). git 머지가 정확히
  이 모델이다.
- **분기 지점은 코드 계보로 정한다 (상현님, 2026-07-23)**: 새 체인을 어느 닫힌 체인에서
  분기할지는 **개념적 독립성이 아니라 "필요한 코드가 어디 쌓였나"**로 정한다. 뷰어와 무관한
  기능이라도 그 기능이 뷰어 체인에 쌓인 코어 개선(예: `gil step --body`)을 필요로 하면,
  뷰어 체인에서 분기해야 그 개선을 물려받는다. git 브랜치가 코드를 물려주므로, 분기 지점이
  곧 상속받는 코드를 정한다.

### 배포 순환 (방을 대체하는 체인 흐름)

정적인 "방(room)" 분류는 없다. 상태는 **지금 어느 체인이 열려 있나**로 표현된다:

```
개발 체인 (개발·실험)
   ↓ 닫힘
스테이징 체인 (필드테스트)   ← 닫힌 개발 체인 끝에서 열림
   ↓ 닫힘
배포 체인 (배포)            ← 닫힌 스테이징 체인 끝에서 열림
   ↓ 닫힘 → 다시 개발 체인    (순환)
```

- **로드맵 (2026-07-24 완료)**: `gil-v3`(gil init 대문) → 첫 개발 체인 → 스테이징 → 배포.
  **이 로드맵은 완주됐다** — v3를 `main`으로 승격(옛 main은 `legacy`·`legacy-main` 브랜치로
  보존), `v3.0.0` 정식 릴리스(latest), `gil migrate`(v2→v3 계보 변환) 신설·검증까지 완료.

### 체인 모드 — 자율 완주 vs 승인 (상현님, 2026-07-23)

체인을 **열 때 한 번** 모드를 정한다. 이후 그 체인의 사이클·스텝은 그 모드로 진행된다.

- **자율 완주(autonomous) — 기본값.** 체인을 완성할 때까지 사람에게 묻지 않고 스스로
  진행한다. 사이클을 열고·스텝을 밟고·닫고, 다음 사이클로 이어간다. 사람은 관전하되
  개입하지 않는다(원할 때 끼어들 수는 있다).
- **승인(approval) — 예외.** 스텝·사이클 결과를 사람이 승인/리젝트해야 넘어간다. 디자인
  판단이 사람 몫일 때 쓴다(예: **뷰어** — 스크린샷·분석 보고서를 올려 승인받기). 리젝트는
  새 가설로 backtrack.

#### pending = human-in-the-loop 데이터화 (상현님, 2026-07-23)

**철칙 (반드시): approval 체인에서는 pending 스텝으로 사람의 승인/기각을 명시적으로 받는다.**
승인/기각 없이 산 잎·죽은 잎을 임의로 확정하지 않는다 — 사람 판단이 필요한 지점은 언제나
pending으로 멈추고 묻는다. 사람 판단이 필요한 지점은 **pending 스텝**으로 명시한다:

1. 에이전트가 접근을 verify까지 밟고, 판단이 필요하면 `--kind pending` 스텝을 새긴다.
2. 에이전트가 사람에게 **승인/기각 두 보기**로 묻는다(사람은 뷰어로 확인 후 답).
3. 답에 따라 가지를 뻗는다:
   - **승인** → `analyze --outcome success` (산 잎, 이 접근 채택).
   - **기각** → `analyze --outcome backtrack --to <조상 define>` (죽은 잎) → 조상 define로
     되돌아가 새 형제 가지(hypothesis)로 다른 접근.

pending은 "진행 중, 사람 대기"를 그래프에 남긴다 — 답이 오면 산 잎 또는 죽은 잎으로 확정된다.
사람의 판단이 스텝 트리에 데이터로 기록되어, **가지를 어디로 뻗을지가 정확히 포착**된다
(v3-view C001의 pending 개념 실현).

체인 루트에 `Gil-Mode: autonomous | approval` 트레일러로 각인한다. 열 때 선택하고, 그
체인 동안 유지된다. **기본은 자율** — 명시 없으면 autonomous.

### 체인별 검증 깊이 (상현님, 2026-07-23)

각 체인은 맡는 검증 깊이가 다르다:

- **개발(dev) 체인의 verify = 기능 검사(smoke)만.** "이 기능이 동작하는가"까지. 전 주기가
  도는지, 명령이 커밋을 새기는지 정도. 빠르게 짓고 돌린다.
- **스테이징 체인 = 기능 검사 이상의 테스트.** 엄밀한 검증·엣지 케이스·필드테스트를 여기서.
  개발 체인이 닫힌 끝에서 열린다.
- **배포 체인 = 봉인·릴리스.** 스테이징이 닫힌 끝에서 열린다.

검증을 두 체인으로 나누면, 개발은 가볍게 전진하고 엄밀함은 스테이징이 맡는다.

## 1. 노드 = 커밋

모든 스텝은 커밋 하나다.

- **제목(subject)**: `gil <chain>/<cycle>/<step> <kind>: <사람이 읽는 요약>`
  예: `gil gil-v3-redesign/C001/s3 verify: trailer 파싱 실증`
- **본문(body)**: 스텝 디테일 (자유 markdown). `git log --format=%b <sha>`로 읽는다.
- **트레일러(trailer)**: 구조 메타 (아래 §2). `git log --format='%(trailers:key=K,valueonly)'`.

산출물(코드·figure·field)이 있으면 그 커밋에 파일로 포함한다. 없으면 `--allow-empty` 노드.

## 2. 트레일러 키셋 (`Gil-` 네임스페이스, 원자적 분리)

키마다 값 하나. 나중에 키를 추가할 여지를 위해 최대한 분리한다.

### 위계 — 모든 스텝 커밋 필수
| 키 | 값 | 뜻 |
|---|---|---|
| `Gil-Chain` | 체인명 | 어느 체인. **없거나 미선언 체인이면 gil이 거부** |
| `Gil-Cycle` | 사이클 id | 어느 사이클 |
| `Gil-Step` | 스텝 id (s1, s2…) | 어느 스텝 |
| `Gil-Kind` | define\|hypothesis\|verify\|analyze\|success\|fail\|pending | 스텝 종류 |
| `Gil-Parent` | 부모 스텝 id \| null | 스텝 트리 부모 |
| `Gil-Falsify` | 반증조건 문자열 | **hypothesis 필수** — 무엇이 관측되면 이 가설이 거짓인가(AIL #1) |
| `Gil-Falsify-To` | 조상 define id | **hypothesis 필수** — 반증 시 되돌아갈 define(AIL #1) |
| `Gil-Verdict` | supported\|refuted | **verify 필수** — 지지/반증. refuted면 success 문법 거부(AIL #1) |
| `Gil-Refutes` | `<chain>/<cycle>/<step>` | 소급 반증 간선 — 이 스텝/사이클이 앞서 닫힌 supported verify 판정을 뒤늦게 반증(AIL #1 B). 여러 줄 허용 |
| `Gil-Deploy-State` | staged \| live | 배포 마커의 상태(이슈 #56). staged = 단위는 확정, 아직 안 올라감. 없으면 live(옛 마커) |
| `Gil-Cycle-Goal` | 자유텍스트 | 사이클 s1 에만. **무엇이 되면 끝인가**(달성 판정 기준, 이슈 #62). 선언하면 close 가 `--goal-met` 을 요구 |
| `Gil-Goal-Met` | true | close 커밋. 선언한 목표에 답하고 닫았다 |
| `Gil-Parallel-With` | 사이클 id (다중) | 사이클 s1 에만. 미해결 사이클을 **알면서** 나란히 연다는 선언(이슈 #45) |
| `Gil-Refines` | `<chain>/<cycle>/<step>` (다중) | 이 스텝/사이클이 **해석만** 정밀화하는 앞 verify·analyze(이슈 #42). 대상 verdict 불변 |
| `Gil-Inherit` | 자유텍스트 | 부모에게서 물려받은 지식·전제·교훈(AIL #3). 계보 간선(--parent/--merge/--refutes/--refines)이 있으면 **필수** |

### 사이클 루트 스텝(s1)에만
| 키 | 값 | 뜻 |
|---|---|---|
| `Gil-Cycle-Author` | 존재명 | 이 사이클을 연 존재 |
| `Gil-Cycle-Parent` | 부모 사이클 참조 \| null | 사이클 계보. **여러 줄 = 사이클 머지(두 조상)** |

### 분석 결과 스텝에만
| 키 | 값 | 뜻 |
|---|---|---|
| `Gil-Outcome` | success \| backtrack \| fail | 분석 결말 |
| `Gil-Backtrack` | 조상 define 스텝 id | backtrack일 때 되돌아갈 곳 |

### 체인/사이클 머지에만 (git 머지 개념 차용)
| 키 | 값 | 뜻 |
|---|---|---|
| `Gil-Merge` | 합류하는 다른 체인/사이클 참조 | **여러 줄. 이 커밋 이후 노드는 양쪽 조상을 상속** |

> **머지 = 두 조상 (상현님, 2026-07-23)**: git 커밋이 머지되면 두 부모를 갖듯, gil 노드도
> 머지되는 순간부터 그 다음 노드들이 두 갈래의 조상을 물려받는다. 체인 간·사이클 간 관계는
> 이 머지로 표현한다. (옛 loom/C015 lineage 머지의 v3 네이티브 실현.)

### 머지는 역순으로 잡힌다 (상현님, 2026-07-23) — 아래 층이 완성돼야 위 층 머지

머지는 **완성된 것들끼리 위 층으로 올라가며** 성립한다. 아래에서 위로:

1. **스텝 머지** — 한 사이클 안 **산 잎들**(analyze/success)이 머지. 여러 산 갈래가 하나로.
   `Gil-Merge`에 합류하는 산 잎 스텝 id들. 이후 스텝은 두 갈래를 조상으로.
2. **사이클 머지** — 닫힌 **산 사이클들**(solved)이 머지. `Gil-Cycle-Parent` 여러 줄.
3. **체인 머지** — 닫힌 **체인들**이 머지. `Gil-Merge`에 체인 참조 여러 줄.

핵심: 산 잎이 모여 사이클을 이루고, 산 사이클이 모여 체인을 이룬다. **완성(산 잎·산
사이클·닫힌 체인)만이 위 층에서 머지 대상**이 된다 — 죽은 잎은 머지되지 않는다(벽의 지도로
남을 뿐). 배포 순환과 맞물린다.

## 3. gil이 방어하는 무결성 (fsck)

gil은 커밋 그래프를 훑어 아래를 검사한다. 위반이면 새 노드 선언을 거부하거나 fsck가 보고한다.

1. **위계 무결성** (상현님 핵심):
   - 체인 없는(=`Gil-Chain` 미선언·미존재 체인) 사이클 선언 거부.
   - 사이클 없는 스텝 선언 거부.
   - `Gil-Parent`가 가리키는 부모 스텝이 실재해야 함 (dangling parent 거부).
   - 스텝 트리에 순환 없음.
2. **id 문법·중복**: chain·cycle·step id는 **소문자**·숫자·하이픈만(git ref 안전, 마침표 금지,
   대문자 금지). 사이클 id는 `c001`처럼 소문자 c + 숫자. 같은 체인에서 사이클 id 중복 금지.
   (옛 R1 계승. 2026-07-23: 손 시연 fsck가 대문자 C001을 잡아 소문자로 통일.)
3. **스텝 순환 규칙**: define→hypothesis→verify→analyze 순환. analyze는 `Gil-Outcome` 강제.
   backtrack이면 `Gil-Backtrack`가 조상 define을 가리켜야 함.
   - **분기 강제(AIL #1, 체인 일자화 결함 해소)**: hypothesis는 `--falsify`(반증조건)와
     `--falsify-to`(반증 시 되돌아갈 조상 define)를 문법으로 요구한다. verify는 `--verdict
     supported|refuted`를 요구하고, refuted면 **success를 거부**한다(fail/backtrack만 허용).
     죽은 잎(fail/analyze-fail/backtrack) 위에는 선형으로 잇지 못하고 새 가지만 허용한다 —
     fail 잎이 지도에 물리적으로 남는다. HEAAL: 분기는 격려가 아니라 success의 좁은 문으로 는다.
   - **소급 반증 간선(AIL #1 B, 사이클 간 늦은 반증)**: 후속 사이클이 앞서 닫힌 supported
     verify 판정을 뒤늦게 반증하면 `--refutes <chain>/<cycle>/<step>`(open·step 양쪽)으로
     계보에 남긴다. verdict 를 뒤집지 않는다(append-only) — 과거 판정은 그 시점의 정직한
     기록으로 불변 보존하고, 반증은 새 사이클에 forward-pointing 간선으로 얹는다("새 진실은
     앞에 산다"). 대상 무결성만 강제: 실재·닫힌 사이클·verify kind·verdict=supported. 미래의
     반증은 문법으로 못 낳으니 강제가 아니라 **가시화** — 뷰어가 그 판정에 ⚠refuted-by 를 붙여
     "흠 없는 success" 착시를 깬다. fsck 는 dangling refutes 대상을 잡는다.
   - **해석 층의 두 표면(이슈 #32·#42, 2026-07-28)**: verify 노드에는 **판정(verdict)과
     해석(원인·방법)** 두 층이 있는데, 위 간선들은 판정 층만 다룬다 — refutes 는 뒤집고,
     backtrack 은 define 까지 완전 회귀한다. 그래서 두 흔한 경우가 표면을 못 가졌다:
     - *판정은 옳고 해석만 불완전했다* — 정직한 탐구는 원인을 점층적으로 좁힌다("언어 공백
       같다" → "아니 문서였다"). refutes 를 걸면 앞 사이클의 유효한 성과까지 부정하는 과잉이
       되고, inherit 로만 두면 정정 관계가 그래프에서 사라진다. → **`--refines
       <chain>/<cycle>/<step>`**(open·step 양쪽). 대상의 verdict 는 **불변**이고, 해석만
       정밀화한다. 대상 무결성: 실재·닫힌 사이클·kind 가 verify 또는 analyze(해석을 담는
       노드). verdict 는 묻지 않는다 — refuted 해석도 더 좁혀질 수 있다. `--inherit` 필수.
       가시화는 양방향: 정밀화한 쪽에 `⤳refines`, 정밀화된 쪽에 `⤳refined-by` — 판정만 읽고
       멈추는 걸 막는다. refutes 가 극성 전환이면 refines 는 해석 심화다.
     - *가설은 맞고 구현·방법만 틀렸다* — 반증에는 두 층위가 있다. 가설 자체가 틀렸으면 define
       완전 회귀가 옳지만, analyze 가 "가설은 유효하고 방법이 틀렸다"를 밝힌 경우 define 까지
       되돌리는 건 **그 분석을 버리는 일**이다. 옛 문법은 재분기 앵커를 define 으로만 받아
       분석의 결론이 재분기의 뿌리가 되지 못했다. → **`hypothesis --to <조상 analyze>`** 허용.
       거부 메시지가 두 갈래를 다 짚는다(가설이 틀렸나 / 방법만 틀렸나).
   - **종결은 잎이다 · 두고 온 가지는 닫을 수 있어야 한다(이슈 #60·#59, 2026-07-28)**:
     append-only 그래프에는 사후 수정 경로가 없다 — 그러니 강제는 **그 순간**에 있어야 한다.
     - 종결 스텝(success/fail) 뒤에는 **선형 부착을 거부**한다. 이어 붙으면 "이 가지는 여기서
       끝났다"는 뜻이 사라지고 뷰어에서도 잎으로 안 보인다. 이어갈 길은 이미 있다 — 조상
       define/analyze 에서 형제 가지(`--to`). 문제는 안 써도 조용히 통과되던 것이었다(실사용:
       같은 상황에서 한 번은 `--to` 를 썼고 두 번은 빠뜨렸는데 도구가 두 경우를 구분하지 않았다).
     - **`--at <스텝>`**: 종결을 **그 잎 자리에** 박는다. HEAD 가 재분기로 떠나면 두고 온 가지를
       영영 못 닫던 결함(이슈 #59). `--to` 는 fail 에서 *부모를 바꾸지 않는다* — "되돌아갈 곳"의
       기록일 뿐이라, 뒤늦게 `--to` 로 닫으려다 **살아있는 success 잎 위에 fail 이 얹힐** 뻔했다.
       자리를 고르는 건 `--at`, 되돌아갈 곳의 기록은 `--to` 로 뜻을 갈랐다. `--at` 대상은 사이클
       전체(모든 가지)에서 찾고, 자식 없는 비종결 잎이어야 하며, 순서 강제도 그 자리 기준으로 본다.
     - **fsck 가 열린 사이클의 매달린 잎도 보고한다**: 옛 검사는 닫힌 사이클만 봤는데 사고는
       열린 사이클에서 났다. 판정은 스텝 번호로 한다 — 형제 가지가 나면 커밋 위상 순서가 뒤집혀
       위상 기반 팁 판정이 엉뚱한 잎을 "작업 중"이라 부른다. 가장 큰 번호가 지금 서 있는 자리다.
   - **잎 상태와 사이클 상태는 다르다(이슈 #62, 2026-07-28)**: 사이클이 끝났다는 건 gil 자신의
     규칙으로 **close 커밋이 있다**는 뜻이다. 그런데 handoff 는 *잎이 다 종결됐는지*만 보고
     "열린 사이클 없음 → 새 사이클을 열거나 체인을 닫아라"로 안내했다. 사람이 기준 문서에
     "완전한 성공 전엔 닫지 마라"고 못박아 일부러 열어둔 사이클이 그렇게 지워졌다.
     handoff 는 세션을 이어받는 첫 관문이라, 이어받은 에이전트는 기준 문서보다 이걸 먼저
     본다 — 그대로 따르면 미완의 사이클을 버려두고 새 사이클로 도망친다(#45 가 막으려는 바로
     그 행동을 도구가 *권유*한 셈이다). 그래서 (a) 닫히지 않은 사이클은 잎이 다 종결됐어도
     그대로 세우고 잎 상태를 따로 적으며, (b) 닫는 길과 더 파는 길을 나란히 주고, (c) 체인의
     기준 문서 — 특히 "하지 마라"로 못박힌 항목 — 를 handoff 가 **인용한다**. 기준을 스스로
     읽기로 마음먹어야만 보는 건 자기규율이고, 자기규율은 원리적으로 불충분하다(#55 와 같은 논리).
   - **목표는 사이클이 들고 있다(이슈 #62 제안 1, 2026-07-28)**: `gil open --goal <달성 기준>`.
     `--purpose` 가 "무엇을 하려는가"라면 `--goal` 은 "무엇이 되면 됐다고 할 것인가"다.
     선언하면 `gil close` 가 **`--goal-met` 으로 그 목표에 답할 것을 요구**하고, 거부 메시지가
     그 목표 문장을 그 자리에서 보여준다. gil 은 달성 여부를 알 수 없다 — 알 수 있는 건
     "답했는가"뿐이고 그것만 강제한다(정직 강제 불가, 은폐 영속화만 차단). 목표에 못 닿았으면
     닫지 말고 갈래를 더 내거나, 막다른 길이면 `--abandon` 이 정직한 자리다. 목표는 매 스텝
     안내와 handoff 에 함께 뜬다 — 판단이 자기확신이 아니라 열 때의 선언에 매이도록.
   - **미해결 define 방치는 거부한다(이슈 #45, 2026-07-28)**: 산 잎 없이 fail 잎만 있고 아직
     안 닫힌 사이클이 있는 체인에서는 **새 사이클 open 을 거부**한다(옛 동작은 경고였고,
     실측에서 4/4 로 도망갔다 — 경고는 읽히지 않거나 읽혀도 다음 줄에서 잊힌다). 세 길을 준다:
     재분기(`hypothesis --to`) · 포기(`close --abandon`) · **선언된 병렬**(`open --parallel <사이클>`).
     병렬은 정당할 수 있으므로 막지 않되 조용히 지나가지도 않게 한다 — 선언은
     `Gil-Parallel-With` 로 그래프에 남는다. 우회가 아니라 **기록되는 판단**이다.
   - **지식 전수 명시(AIL #3)**: 계보 간선이 *새로 생기는* 자리 — 새 사이클(`open --parent`),
     소급 반증(`open/step --refutes`), 머지(`step --merge`) — 에서 `--inherit <전수>`를 요구한다.
     부모에게서 물려받은 사전지식·전제·교훈을 명시하고 출발한다. 같은 사이클 안 선형 스텝은
     직전 `Gil-Parent`로 이어져 전수랄 게 없어 **면제**(매 스텝 강제는 형해화만 낳는다). 체인은
     부모가 위상 유도라 `--inherit` 선택+안내. `--refutes`의 inherit는 '물려받음'이 아니라
     '뒤집음' — 무엇을 뒤집고 무엇은 계승하나. 간선의 존재는 문법이, 내용의 진실성은 존재가.
   - **복합가설 거부(AIL #1 A)**: `--falsify` 가 개행/세미콜론으로 여러 주장을 열거하면 거부한다
     (verdict 는 하나뿐 → 부분반증 은폐). 주장마다 형제 hypothesis 로 갈라 부분반증을 "가지의
     부분 생존"(H1 죽은 잎·H2/H3 산 잎)으로 표현한다.
4. **계보 참조 무결성**: `Gil-Cycle-Parent`·`Gil-Merge`가 실재하는 사이클/체인을 가리켜야 함
   (옛 R6의 v3판, C041 이월).

## 3.1 거부는 "다음 올바른 한 수"를 준다 (이슈 #47, 2026-07-28)

gil 의 힘은 **거부**에서 나온다(HEAAL: 규율은 안내가 아니라 문법의 거부로). 그런데 거부가
"하지 마"까지만 하면, 전진 편향이 있는 사용자 — 특히 LLM — 은 막힌 곳을 **우회**하려 들지
도구가 원하는 길로 가지 않는다. 실사용에서 fail 뒤 4/4 가 재분기 대신 새 사이클로 도망쳤다.

**거부 메시지는 LLM 이 읽는 프롬프트다.** 그러니 모든 거부는 셋을 담는다:

1. **왜** 막혔는지 (규율의 근거)
2. **지금 고를 수 있는 실제 후보** (그 사이클의 define 목록, 유효 kind, 받는 플래그…)
3. **다음 명령** — 복사해 쓸 수 있는 형태로

거부가 거부로 이어지면 안 된다. `chain-close` 가 "c001 이 안 닫혔다"고만 하면 사용자는
`gil close` 를 시도했다 또 거부당한다(fail 잎만 있으면 close 도 거부). 그래서 chain-close 는
사이클마다 **왜 못 닫히는지 들여다보고** 갈 길을 짚는다 — 산 잎이면 close, fail 잎뿐이면
재분기/포기, pending 이면 사람 승인, 미종결이면 그 가지를 끝까지.

**형식 때문에 거부하지 않는다.** 뜻이 명백한데 표기가 다른 건 사고의 문제가 아니라 표기의
문제다. `--to`·`--falsify-to` 는 짧은 이름(`s1`) 외에 경로형·커밋 해시도 받아 정규화한다.

## 4. 명령 표면 (gil이 구현할 것)

손 시연으로 규약을 확립한 뒤 이 명령들을 빌드했다 (구현 완료 — 전체 표면은
[docs/gil/commands.md](../../docs/gil/commands.md)):

- `gil init` — 무에서 세팅(대문 + refs/gil/global + 존재의 방).
- `gil chain <name> --purpose <P>` / `gil chain-close <chain>` — 체인 개설/완결.
- `gil open <chain>/<cycle> --author <who> [--parent <cyc>...]` — 루트 define 커밋 새김.
- `gil step --kind <k> [--outcome <o>] [--to <define>]` — 스텝 전이 커밋.
- `gil approve` / `gil reject` — pending 에 대한 사람의 명시적 승인/기각.
- `gil close [--verdict <v>]` — 산 잎 봉인. `gil chain-merge` — 두 갈래 합류(양쪽 조상).
- `gil log [<chain>] [--all] [--depth chain|cycle|step]` — 커밋 그래프 조회. **뎁스별 전체맵
  (AIL #2)**: `--depth chain`=체인 계보 트리, `cycle <chain>`=사이클+status, `step`(기본)=스텝
  나열. 뷰어 HTML 4패널과 **같은 집계원**(chainsFromGraph·cyclesOf·chainParents)을 텍스트로
  공유 — 인간(뷰어)과 AI(gil log)가 동일 정보를 본다. 무플래그로도 맨 위에 **분기 신호**
  (`분기 체인 M · 사이클 K · 스텝 N | 죽은잎 D`)를 강제로 얹어 일자 편향을 안 찾아도 드러낸다.
  체인·사이클 분기 0이면 경고. `gil fsck` — §3 무결성 검사.
- `gil global` / `gil memory` — 존재·기억(refs/gil/global) 갱신. `gil handoff` — 세션 부활.
- `gil migrate --from <v2-ref> [--prefix <접두>]` — 옛 v2(폴더·cycle.yaml) 이력을 v3 커밋
  그래프로 이주(도구 레벨·범용).

각 명령은 **git 커밋을 새기고 trailer를 붙이는 얇은 래퍼**다. 진실원은 언제나 커밋 그래프.

### 3.2 "이어받음"은 닫힌 끝에서 태어났을 때만 (이슈 #53·#54, 2026-07-28)

체인 계보는 git 조상관계에서 읽지만, 조상관계만으로는 두 가지가 구분되지 않는다:

- **진짜 계승** — 앞 체인을 `chain-close` 로 닫고 그 끝에서 새 체인을 연다(배포 순환).
- **병렬 작업** — 앞 체인이 아직 열려 있는데 옆에서 다른 줄기를 시작한다.

둘 다 git 에서는 "새 브랜치가 HEAD 에서 갈라진" 같은 모양이다. 그래서 옛 코드는 병렬까지
*"부모 체인 X 에서 이어받음"* 이라고 **단언**했다. 실측: v2 에서 `parent: null` 인 독립 체인
5개가 이주 뒤 한 줄로 이어졌고, 같은 기간 서로 다른 장비에서 굴리던 트랙들이 이어받음으로
각인됐다 — **그런 이어받음은 없었다.**

**판정 규칙**: 자식 루트에서 첫 부모를 거슬러 올라가다 처음 만나는 다른 체인의 커밋이 그
체인의 `chain-close` 이면 계승, 아니면 병렬(계보를 그리지 않는다).

판정은 **만들어진 순간** 기준이어야 한다. "부모가 지금 닫혀 있나"로 보면 나란히 시작한 체인도
앞 체인이 나중에 닫히는 순간 소급해서 자식이 된다.

없는 계보를 그리느니 안 그린다 — **없는 성공을 날조하지 않는다**(§4.1.1)와 같은 원칙이다.
병렬을 1급으로 *표현*하는 문법(동시 트랙 선언)은 아직 없다. 지금은 "없다고 말하지 않는" 데까지다.

### 4.0.1 체인 생애주기 — 인터뷰에서 회고까지 (이슈 #33, 2026-07-28)

체인은 **사람의 기준**으로 열리고 **그 기준 대비 회고**로 닫힌다. 강제선은 딱 두 곳이다:

| 지점 | 강제 | 왜 |
| --- | --- | --- |
| `gil open` | 인터뷰로 확정된 기준(`Gil-Interview: done`) 없으면 거부 | 열 때 LLM 이 스스로 기준을 정하지 못하게 |
| `gil chain-close` | 기준이 있는 체인은 `--retro` 없으면 거부 | 닫을 때 '됐다'가 자기확신이 되지 못하게 |

**비대칭이 아니라 대칭이다.** 인터뷰만 강제하고 회고를 안 걸면, 체인은 열 때만 사람의 기준에
매이고 닫을 때는 LLM 판단으로 끝난다 — 생애주기의 반쪽이 빈다.

**소급하지 않는다.** 기준 없이 열린 옛 체인은 회고 없이 닫힌다. 없는 잣대에 대고 성적표를
요구하면 형식만 채운 빈 문서가 나온다(v3.1.0 falsify 가 준 교훈).

**시드는 기준이 아니다.** `--seed` 는 회고에서 자란 다음 물음이고, 다음 `gil chain` 이 그걸
건네주며 "이걸로 인터뷰 질문을 짜라"고 안내한다. 시드를 그대로 레퍼런스로 삼는 지름길은
열지 않는다 — 그건 사람 우회다. 트레일러: `Gil-Retro` · `Gil-Seed-Ref`.

```
인터뷰(기준) → 사이클들 → 회고(기준 대비) → 시드 → 다음 체인의 인터뷰
```

### 4.1 MCP 표면 — `gil mcp serve` (2026-07-28)

CLI 와 **같은 함수**를 MCP 툴(`gil_chain`·`gil_open`·`gil_step`·`gil_close`·`gil_chain_close`·
`gil_approve`·`gil_reject`·`gil_log`·`gil_fsck`·`gil_handoff`·`gil_deploy`·`gil_interview`·
`gil_interview_status`)로
노출한다. 규율(인터뷰 필수·pending 잠금·falsify 강제…)이 두 표면에서 갈라지지 않도록 래퍼는
얇게 — 검증은 한 곳에만 산다.

**왜 MCP인가.** 인터뷰가 두 채널로 쪼개져 있었다: LLM 은 대화창에서 질문지를 만들고 사람은
뷰어 폼에서 답한다. 둘이 서로를 모르니 LLM 은 pending 인 줄 모르고 또 질문지를 만들었고
(실사용 붕괴, gil-test-2), 사람은 127.0.0.1 링크·포트충돌과 씨름했다. MCP 에서는 한 홉이다 —
`gil_interview` 가 호스트의 **Elicitation**(네이티브 폼)으로 그 자리에서 묻고 답을 받아
레퍼런스를 확정한다. 대기가 하나뿐이라 "두 대기가 따로 논다"는 실패가 구조적으로 불가능하다.
폼이 `accept` 로 돌아오지 않으면 — 호스트가 못 띄웠든 사람이 취소했든 — 기준은 만들어지지
않고(LLM 이 대신 답하는 길은 열리지 않는다) 질문은 옛 뷰어 경로(pending 커밋)로 심겨 남는다.

**단언하지 않는 것이 규범이다(이슈 #57).** 서버는 폼이 사람 화면에 뜬 적이 있는지 알 수 없다 —
실사용에서 Claude Code 가 폼을 렌더하지 못한 채 즉시 `decline` 을 돌려줬고, gil 은 그걸 "사람이
decline 했다"고 단언했다. 구분 못 하는 것을 단언하면 에이전트에게 **없던 사람 의사가 심기고**,
그게 "사람이 원치 않으니 내가 기준을 쓰자"는 우회 압력이 된다. 레일이 사람 의사를 잘못 전달하면
레일을 뚫는 게 합리적으로 보이기 시작한다. 그래서 사실만 적고(무엇이 돌아왔는지) 다음 한 수를
준다.

**기다림에는 수단이 따른다(이슈 #58).** 뷰어 폼 제출은 자동 통지되지 않는다 — MCP 툴은
요청-응답이라 스스로 깨어나지 못한다. "답을 기다려라"만 말하면 에이전트는 바쁜대기(무의미한
`git log` 반복)나 우회로 밀린다. 그러니 기다림을 실행 가능한 것으로 만든다:
`gil interview <chain> --status`(`pending|done`, MCP `gil_interview_status`)와
`gil interview <chain> --wait [--timeout <초>]`(제출될 때까지 블록 후 확정 기준을 반환).
시간초과는 실패가 아니라 "아직 pending" 이며, 그때도 기준을 대신 쓰라고 하지 않는다.

**제약 두 가지.** (a) stdout 은 JSON-RPC 전송선이라 모든 출력이 버퍼로 간다(`outRaw`).
(b) 거부(`die`)가 프로세스를 죽이면 첫 거부에서 세션이 끊긴다 — MCP 모드에서 `die`/`gilExit`
는 그 호출만 끝낸다(`gilAbort`). 거부는 gil 의 본체이므로 거부 뒤에도 대화가 이어져야 한다.

의존성은 공식 Go SDK(`modelcontextprotocol/go-sdk`) 하나뿐이고, CGO 없이 5타깃 전부
정적 단일 바이너리가 유지된다(§지원 플랫폼 불변).

### 4.1.1 이주의 정직 — 없는 성공을 날조하지 않는다 (이슈 #50, 2026-07-28)

`gil migrate` 의 verdict 매핑은 **명확한 것만 접는다**:

| v2 verdict | v3 종결 kind |
| --- | --- |
| `supported` · `success` | `success` (산 잎) |
| `rejected` | `fail` (죽은 잎) |
| **그 밖의 전부** (`partial` · `inconclusive` · verdict 없음 · 미지의 값) | `pending` (사람 판단 대기) |

옛 매핑은 결론이 아닌 것들을 전부 `success` 로 접었고, 실사용 저장소에서 **71 사이클 중
18개(25%)가 "산 잎"으로 둔갑**했다. 그 순간 이주된 이력은 원본보다 **낙관적인 거짓말**이 된다.
`close --abandon` 이 지킨 원칙("없는 성공을 날조하지 않는다")은 이주에서도 같다.

`pending` 은 "모른다"가 아니라 **"이건 사람이 봐야 한다"** 는 정직한 표식이다 — 결론이 없던
사이클에 정확히 들어맞는다. 원본 verdict 문자열은 종결 스텝 본문에 보존되므로 잃지 않는다.
원 verdict 문자열은 종결 커밋의 `Gil-V2-Verdict` 트레일러에 **무손실 보존**된다 — 매핑 정책이
뒤에 바뀌어도 여기서 복구할 수 있고, `inconclusive` 와 `partial` 이 그래프 위에서 구분된다
(본문 산문은 기계가 못 읽는다).

**범위는 사람이 제어한다.** v2 `fsck` 는 동결해 둔 옛 체인(`legacy/archived-chains/…`)을 세지
않는데 migrate 는 끌어와 라이브 v3 체인으로 만들었다. 동작이 틀린 게 아니라 **제어가 없던
것**이 문제다 — `--exclude <경로조각>`(여러 번 가능)으로 뺀다.

`--dry-run` 이 **이주 전에** 전부 보여준다: 어디서 몇 개를 가져왔는지, 무엇을 제외했는지,
사람 판단 대기가 몇 개이고 어떤 것들인지, 그리고 다음 한 수(`gil approve` / `gil reject --to`).
제외도 **조용히 하지 않는다** — 조용한 누락도 조용한 실패다.

### 4.2 MCP Apps — 뷰어를 호스트 안으로 (SEP-1865, 2026-07-28)

뷰어의 마찰은 늘 **바깥**에 있었다: `127.0.0.1:8790` 이라는 날 주소를 사람이 못 알아보고,
포트가 충돌하면 시스템 브라우저로 새고, 샌드박스 호스트에선 아예 안 열렸다. MCP Apps 는 그
바깥을 없앤다 — 서버가 `ui://` 리소스로 HTML 을 내주면 호스트가 자기 안의 샌드박스 iframe 에
직접 그린다. 주소도 포트도 브라우저도 없다.

계약(규범 문자 그대로 — 하나만 어긋나도 호스트는 **조용히** 안 그린다):

| 항목 | 값 |
| --- | --- |
| 리소스 URI | `ui://gil/graph` |
| mimeType | `text/html;profile=mcp-app` |
| 툴→UI 고리 | `gil_graph` 의 `_meta.ui.resourceUri` |
| 확장 선언 | initialize 캐퍼빌리티 `extensions["io.modelcontextprotocol/ui"].mimeTypes` |
| iframe↔호스트 | postMessage 위 JSON-RPC (`ui/initialize` 핸드셰이크, `ui/notifications/*`) |

**신선도에 대한 정직성.** 체인 그래프 SVG 레이아웃은 Go 가 그린다(`chainLayout`). "빈 껍데기 +
데이터 주입"으로 쪼개려면 레이아웃을 JS 로 이중화해야 하는데, 그 이중화가 나중에 어긋나는
종류의 빚이다. 그래서 리소스를 **읽는 시점에 통째로 렌더**한다(읽는 순간의 데이터는 언제나
최신). 대신 호스트가 템플릿을 캐시해 낡은 화면이 남을 수 있으므로, 페이지가
`ui/notifications/tool-result` 로 최신 팁 서명을 받아 자기 것과 다르면 **낡았다고 스스로 밝힌다**.
살아있는 척하지 않는다 — 낡음을 숨기는 화면이 없는 화면보다 나쁘다.

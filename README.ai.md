# README.ai.md — 에이전트 자가 온보딩 (gil v3)

**너는 AI 에이전트다.** 사람이 이 문서를 건넸다. 그게 지시의 전부다: **읽고, 실행하라.**
그들은 명령을 몰라도 된다 — 네가 안다.

> **⭐ 총괄 강령 — 이 온보딩은 한 번에 끝까지 흐르는 하나의 절차다. 중간에 멈추지 마라.**
> 아래 Step 0 → A → B → C 를 **끊김 없이 자율로 수행하라.** 각 Step 은 **너의 행동 지시**이지
> "사용자에게 출력할 한 줄"이 아니다. 특히 **질문 한 줄을 던지고 거기서 정지하지 마라** — 물음은
> 대화를 여는 것일 뿐, 물은 뒤에는 **같은 턴에서 곧바로 다음 행동(소개·설치·세팅)으로 이어가라.**
> 사람의 답을 받아야만 멈추는 지점은 **딱 두 곳뿐**이다:
> 1. **Step 0-4 — 설치 동의** (*"설치해서 시작해볼까요?"*) — **끊김 없이 흐르라는 말은 설치를
>    서두르라는 말이 아니다.** 0-2·0-2b(gil이 뭔지 · 왜 필요한지)를 먼저 다 하고 물어라.
> 2. **Step C — 어떤 문제를 풀지** (*"어떤 작은 문제부터?"*)
> 이 두 곳 외에는 **어떤 질문에서도 멈추지 말고** 스스로 판단해 진행하라. *도구를 어떻게 쓰는지*는
> 절대 사람에게 묻지 마라. (실측: 첫 물음 한 줄만 찍고 정지해버리는 실패가 있었다 — 그러지 마라.)

사람용 문서: [English](README.md) · [한국어](README.ko.md) · gil 사용법 전체:
[QUICKSTART](project/gil-v3-redesign/QUICKSTART.md)

> **네 호스트가 MCP 를 지원하면** — 이 온보딩을 마친 뒤 [MCP.ai.md](MCP.ai.md) 로 이어가라.
> gil 을 명령줄이 아니라 **툴로 직접** 부르게 되고, 무엇보다 인터뷰(기준 세우기)가 호스트의
> 네이티브 폼으로 그 자리에서 사람에게 물어진다 — 대화창과 뷰어로 쪼개져 있던 두 채널이
> 하나가 된다.

## 이게 뭔가 (10초)

**gil** (길 · GIt for Language model) — 너(LLM)가 어려운 문제를 작고 재현 가능한 **사이클**의
**체인**으로 정복하게 한다. 문제정의(define) → 가설(hypothesis) → 검증(verify) → 분석(analyze)
→ 종결(success/fail). git이 소스 역사를 다루듯, gil은 *사고의 역사*를 다룬다. 위계(체인·사이클·
스텝·분기)는 전부 **진짜 git 브랜치와 커밋 그래프**로 남는다 — 재현·검증 가능하고, 그래프로
되돌아볼 수 있다. 네가 일을 하고, gil이 *왜 그렇게 했는지*를 영구히 기록한다.

## Step 0 — 사람을 온보딩하라 (아무것도 설치하기 전에)

위 문단은 **너를 위한** 것이다. 이 URL을 건넨 사람은 *"읽고 따르라"*는 말만 들었을 뿐,
**gil이 뭔지·곧 자기 컴퓨터에 뭔가 깔린다는 것**을 모를 수 있다. **조용히 설치부터 시작하지
마라.** 그런데 **질문부터 던지지도 마라** — 다짜고짜 *"gil 처음 쓰시나요?"* 로 시작하면 사람은
"누가, 왜, 뭘 묻는 거지?" 하고 당황한다. **먼저 나를 소개하고 → 무슨 문서인지·gil이 뭔지
설명하고 → 그다음에 물어라.** 아래 0-1~0-4 를 **이 순서대로, 사람의 언어로**(그들이 한국어면
한국어로) 한 흐름으로 낸다. (0-1·0-2 는 멈춤 없이 흐르는 오프닝이다 — 위 총괄 강령.)

### 0-1. 나를 소개하라 (첫 인사)

**질문이 아니라 인사로 연다.** 예: *"안녕하세요, 저는 앞으로 당신과 함께 이 작업을 이어나갈
**clew**(클루)입니다."* — 담백하게 한 문장. (기본 존재 이름은 `clew`다. 아직 설치 전이라
존재가 확정되진 않았지만, 함께 일할 상대로 나를 먼저 소개해 사람이 편해지게 한다.)

### 0-2. 무슨 문서인지 · gil이 뭔지 설명하라

이어서 **사람이 방금 무엇을 나에게 건넸는지** 알려준다. 예: *"방금 저에게 주신 문서는
**gil**(길)이라는 작은 프로그램에 대한 안내예요."* 그리고 gil 을 **사람의 언어로** 소개한다:

> *"gil 은 제가 당신의 문제를, 당신이 지켜보고 되돌려볼 수 있게 풀어주는 도구예요. 예를 들어
> 데이터 분석을 맡기시면 저는 '이 가설을 세우고 → 이렇게 검증했고 → 결과는 이랬다'를 **단계마다
> 기록**해요. 나중에 '왜 이렇게 했지?'가 궁금하면 그 사고 과정을 그래프로 그대로 되짚어볼 수
> 있어요. 데이터 분석·버그 사냥·연구·리팩터처럼 신중히 풀고 되돌아볼 가치가 있는 일에 좋아요."*

**안심도 함께** (컴맹도 겁먹지 않게, 무엇이 일어나는지 솔직히):
- 설치되는 건 **작은 프로그램 하나(`gil`)** 뿐이다 — 백신 깔듯 시스템을 건드리지 않는다.
- **안전하다** — 공개된 체크섬으로 무결성을 검증하고 받는다(위조되면 설치가 멈춘다).
- 필요한 건 **git**(표준 무료 도구) 하나뿐. 없으면 내가 설치를 도와준다.
- **언제든 멈출 수 있고**, 남는 건 작업 폴더 안에 다 있다 — 원하면 통째로 지우면 그만이다.

(원하면 둘러볼 링크 — 강요 말고 "관심 있으시면": 프로젝트
https://github.com/hyun06000/Ariadne · 라이브 예시 그래프
https://hyun06000.github.io/ariadne-example/ 는 AI 가 실제 데이터(UC Berkeley 입학, 심슨의
역설)를 gil 로 분석해, 첫 가설이 *틀려* 죽은 잎으로 남고 되돌아가 정답에 이른 과정이 보인다.
*"지금 안 보셔도 돼요 — 설치하면 제가 직접 예제를 돌려 눈앞에서 보여드릴게요."*)

### 0-2b. **왜 이게 필요한지** 납득시켜라 (설치보다 먼저 — 예외 없음)

**설치를 먼저 하려고 하지 마라.** gil이 *무엇인지* 설명하는 것과 사람이 *왜 이게 필요한지*
납득하는 것은 다르다. 납득 없이 깔린 도구는 다음 세션에 지워진다 — 그리고 무엇보다, 자기
컴퓨터에 뭐가 왜 들어오는지 모르는 채로 동의를 받아내는 건 동의가 아니다.

사람의 **지금 상황에 붙여서** 필요성을 말하라(일반론 말고). 쓸 수 있는 근거들:

- **"세션이 끝나면 제 사고는 증발합니다."** 오늘 제가 무엇을 시도했고 무엇이 *실패했는지*는
  다음 대화의 저에게 남지 않는다. gil은 그걸 git 커밋으로 남겨 다음 세션의 제가 이어받게 한다.
- **"제 말을 검증할 수단을 드립니다."** 제가 '분석해봤더니 이렇습니다'라고 하면 지금은 믿는
  수밖에 없다. gil을 쓰면 가설·검증·죽은 가지가 그래프로 남아 **되짚어 반박**할 수 있다.
- **"막다른 길을 두 번 걷지 않습니다."** 실패한 가지가 기록으로 남아, 되돌아가야 할 때
  어디로 되돌아갈지가 남는다.
- **값하지 않는 경우도 솔직히 말하라** — 한 줄 질문·단순 편집·급한 일에는 gil이 과하다.
  *"이번 일엔 굳이 안 쓰셔도 됩니다"* 라고 말할 수 있어야 그 반대말도 믿을 만해진다.

그리고 **사람이 물으면 거기서 설치를 보류하고 답하라.** "이거 안전해요?" "뭐가 깔려요?"
"그냥 평소처럼 하면 안 되나요?" — 이 질문들에 다 답하기 전에 설치 명령을 내리지 마라.
**납득 → 동의 → 설치** 순서다. 순서를 앞당겨서 얻는 건 없다.

### 0-3. 이제 물어라: gil을 처음 쓰나?

소개를 마쳤으니 **여기서 처음으로 사람에게 묻는다** — *"gil 을 처음 쓰시나요? 처음이시면 제가
더 상세히 안내해 드릴게요. 써보셨다면 빠르게 설정만 도와드릴게요."* 이건 톤을 맞추기 위한
물음이지 **멈춤 지점이 아니다**(멈춤은 0-4 동의와 Step C 딱 둘, 총괄 강령). 답이 오면 그에 맞춰,
안 와도 기본(처음 쓰는 사람)으로 가정해 **바로 다음으로 이어간다.**

### 0-4. 설치 동의를 받아라 (첫 멈춤 지점)

***"그럼 gil을 설치해서 시작해볼까요?"*** — 사람의 허락을 구하는 **첫 멈춤 지점**이다.
**0-2·0-2b(설명·필요성)를 마치기 전에는 이 물음을 꺼내지 마라** — 설명 없이 받은 "네"는
동의가 아니라 체념이다. 사람이 망설이거나 되물으면 **설치를 미루고** 그 물음부터 답하라.
답이 "아니오"거나 "나중에"면 그것도 정상 종료다 — 설득을 반복하지 말고, gil 없이 지금 일을
도와주고 **필요해질 때 다시 제안하라**. 동의하면
Step A(설치)·B(세팅)를 자율로 진행하라. 매 단계를 질문으로 만들지 마라(사람이 명령을 몰라도
되는 게 핵심이다). 설치 직후엔 **Step B.1(관전 창 켜기)**로 뷰어를 띄운 뒤, Step C에서
사람에게 **개시 인터뷰**로 무엇을 풀지·무엇이 관측되면 풀린 것인지를 묻는다. (연습용 데모
사이클은 만들지 마라 — 진짜 문제를 처음부터 제대로 하는 것이 최고의 시연이다.)

> 예시(사람의 언어로 각색): *"gil 처음이시죠? 간단히 설명드릴게요 — 제가 당신의 문제를 작은
> **사이클**들로 풀면서 '왜 이렇게 했는지'를 단계마다 기록하는 도구예요. 되돌려보고 그래프로
> 볼 수 있고요. 설치되는 건 체크섬 검증된 작은 프로그램 하나뿐이고, 언제든 멈추거나 지울 수
> 있어요. 궁금하면 프로젝트(github.com/hyun06000/Ariadne)나 라이브 예시 그래프(hyun06000.github.io/
> ariadne-example)를 둘러보셔도 되고요. **설치해서 시작해볼까요?**"*

## Step A — gil 설치 (지금 하라)

플랫폼을 감지해 맞는 바이너리를 받는다. Python도, 툴체인도 필요 없다.

> **먼저 플랫폼을 가른다.** macOS·Linux(및 WSL) → 아래 POSIX 블록. **Windows(PowerShell)
> → 맨 아래 Windows 블록으로 곧장 가라.** POSIX 한 줄·손 블록은 Windows 기본 셸에선 안 돈다
> (Git Bash 로 돌리면 리눅스 바이너리를 잘못 받는다 — install.sh 가 이를 감지해 막는다).

**macOS·Linux — 가장 짧게** — 설치 스크립트 한 줄. 플랫폼 감지·다운로드·체크섬 검증을 다 하고,
**호스트 PATH(`~/.local/bin`)에 설치**한다 — `git`처럼 어느 저장소에서든 `gil`로 잡힌다:

```bash
curl -fsSL https://raw.githubusercontent.com/hyun06000/Ariadne/main/install.sh | sh
gil help                             # ← 이 빌드가 실제로 뭘 하는지 도구에 물어라. 문서로 추측 말 것.
```

> **`gil`이 안 잡히면**(`command not found`) `~/.local/bin`이 PATH에 없는 것 — install.sh가
> 그 경우 PATH 추가 한 줄을 안내한다. 그대로 따르거나, 당장은 `~/.local/bin/gil help`로 실행하라.
> **저장소별로 gil을 고정**하고 싶으면 `... | sh -s -- --dir .`로 저장소-로컬(`./gil`) 설치도 된다.

또는 **한 단계씩 (같은 동작을 손으로 — 이건 현재 폴더에 `./gil`로 받는다)**:

```bash
os=$(uname -s | tr '[:upper:]' '[:lower:]')
case "$os" in darwin) os=darwin;; linux) os=linux;;
  mingw*|msys*|cygwin*) echo "Windows 다 — 아래 PowerShell 블록을 써라"; exit 2;; *) os=linux;; esac
arch=$(uname -m); case "$arch" in arm64|aarch64) arch=arm64;; *) arch=amd64;; esac
sha() { if command -v shasum >/dev/null 2>&1; then shasum -a 256 "$@"; else sha256sum "$@"; fi; }
base=https://github.com/hyun06000/Ariadne/releases/latest/download
curl -fsSL -O "$base/gil-${os}-${arch}"
curl -fsSL -O "$base/SHA256SUMS"
grep " gil-${os}-${arch}\$" SHA256SUMS | sha -c - && mv "gil-${os}-${arch}" gil && chmod +x gil
./gil help
```

**체크섬 단계는 필수 — 건너뛰지도, "간소화"하지도 마라.** 해시가 어긋나면 `&&` 사슬이 끊겨
`gil`이 실행 가능해지지 않는다. 검증 안 된 건 아무것도 못 돈다. 릴리스 직후 불일치는 CDN이
아직 따라잡는 중이니 **~60초 기다렸다 블록을 다시 실행**하라. 체크를 없애서 우회하지 마라.

**Windows (PowerShell, `bash`/`uname`/`curl` 없음)** — 위 블록은 안 돈다. POSIX 셸이 없음을
감지하고 PowerShell로, 같은 필수 체크섬 게이트를 써라(해시가 맞아야만 `gil.exe` 생성):

```powershell
Invoke-WebRequest https://github.com/hyun06000/Ariadne/releases/latest/download/gil-windows-amd64.exe -OutFile gil-dl.exe
Invoke-WebRequest https://github.com/hyun06000/Ariadne/releases/latest/download/SHA256SUMS -OutFile SHA256SUMS
$want = ((Select-String -Path SHA256SUMS -Pattern 'gil-windows-amd64\.exe$').Line -split '\s+')[0]
$got  = (Get-FileHash gil-dl.exe -Algorithm SHA256).Hash.ToLower()
if ($got -ne $want) { Remove-Item gil-dl.exe; throw "checksum mismatch — CDN이 따라잡게 ~60초 뒤 재시도; 절대 건너뛰지 말 것" }
Move-Item -Force gil-dl.exe gil.exe
.\gil.exe help
```

> 이 블록은 현재 폴더에 `gil.exe` 를 만든다. **어디서든 `gil` 로 쓰이게 하려면**(그리고 사람이
> 직접 붙여넣을 블록이 필요하면) — PATH 등록·git 설치까지 포함한 사람용 전체 절차가
> [docs/INSTALL.md](https://github.com/hyun06000/Ariadne/blob/main/docs/INSTALL.md#windows-powershell) 에 있다.

### 권한이 막으면 (자주 있는 일 — 여기서 멈추지 마라)

`curl`·바이너리 실행을 네 런타임 권한/샌드박스가 막을 수 있다(Step 0의 사람 동의와 별개 — 네
환경이 거는 기술적 게이트다). 두 갈래로 갈린다:

- **대화형이라 승인 프롬프트가 뜨면** — 한 번 승인하고 이어가라. *"진행할까요?"*를 다시 따지지 마라.
- **프롬프트 없이 그냥 거부되거나(자동승인 분류기) 비대화형이라 승인 경로가 없으면** — 재시도로는
  안 뚫린다. 우회하지 말고 **아래 둘 중 하나로 폴백하라**:
  1. **사람에게 권한 규칙을 요청** — 프로젝트의 `.claude/settings.local.json` 에 아래를 넣고
     세션을 다시 시작하게 안내하라(이 파일은 네가 대신 써줘도 된다):
     ```json
     { "permissions": { "allow": ["Bash(curl:*)", "Bash(gil:*)", "Bash(./gil:*)", "Bash(shasum:*)", "Bash(chmod:*)", "Bash(git:*)"] } }
     ```
  2. **사람이 직접 설치** — 위 설치 한 줄(또는 손 단계 블록)을 사람이 터미널에서 직접 실행하고,
     "됐다"고 하면 너는 **Step B(`gil init`)부터 이어받아라**. 설치만 사람 손을 빌리고 나머지는 네가 운전한다.

어느 쪽이든 **진입 실패로 끝내지 마라** — 폴백 경로를 사람에게 명확히 제시하는 것까지가 Step A다.

### 네가 스스로 설치를 거부할 때 (정규 분기 — 실패 아님)

권한 게이트와 별개로, **네 판단**이 "검증되지 않은 제3자 저장소의 스크립트·실행파일을 확인
없이 실행할 수 없다"고 말할 수 있다. **그 거부는 옳다. 우회하지 마라** — 체크섬을 지우지도,
다른 다운로드 수단을 찾지도 마라. 대신 역할을 나눈다: **너는 검증하고, 실행은 사람이 한다.**

1. 사람에게 거부 사유를 한두 줄로 말한다("제가 대신 실행하진 않겠습니다 — 대신 검증해
   드리고, 실행은 직접 하시는 게 안전합니다").
2. **검증을 실제로 해준다**(읽기만 하므로 네 정책 안이다):
   - `install.sh` 를 페치해 **읽고**, 무엇을 하는지 요약한다(100줄 남짓 — 플랫폼 감지·
     다운로드·체크섬 게이트가 전부다). Windows면 PowerShell 블록을 대신 읽어준다.
   - 릴리스의 `SHA256SUMS` 를 가져와 **사람이 대조할 기대 해시**를 알려준다.
   - 자산 이름·출처를 릴리스 페이지와 `llms.txt` 로 확인한다.
3. 사람에게 **[docs/INSTALL.md](https://github.com/hyun06000/Ariadne/blob/main/docs/INSTALL.md)**
   의 블록을 그대로 붙여넣게 안내한다(Windows=PowerShell, macOS·Linux=한 줄 또는 손 블록).
4. 사람이 "됐다"고 하면 `gil version` 결과를 확인하고 **Step B(`gil init`)부터 이어받아라.**

설치 한 걸음만 사람 손을 빌리고, 그 앞의 검증과 그 뒤의 운전은 전부 네가 한다.

**git이 필요하다.** v3 gil은 위계 전체를 진짜 git 브랜치·커밋으로 남긴다 — git 없이는 동작하지
않는다. `gil`을 처음 실행할 때 git이 없으면 gil이 이 OS 용 설치 명령을 콕 집어 알려주고 멈춘다
(그 안내를 그대로 따르면 된다). git이 없으면 **먼저 설치부터** 안내하라 — 가능하면 자동으로:

- **Windows**: `winget install --id Git.Git -e --silent` 를 시도하라(`--silent` 로 설치관리자
  창·여러 콘솔 창이 번쩍이지 않게 — 비개발자 사용자가 계단식 cmd 창에 공포를 느낀 실사용
  피드백). winget이 없으면(구형 Windows) — https://git-scm.com/download/win 에서 설치 프로그램을
  받게 사람에게 안내하라. (설치 후 새 PowerShell 창을 열어야 PATH가 갱신된다.)
- **macOS**: `brew install git` (Homebrew 있으면) 또는 `xcode-select --install`.
- **Linux**: `sudo apt-get install -y git` / `sudo dnf install -y git` / `apk add git` 등 배포판 패키지.

설치 뒤 `git --version` 으로 확인하고 같은 명령을 다시 실행하라. (`gil init`이 빈 폴더에서
`git init`까지 해주지만, git 실행파일 자체는 있어야 한다.)

> **이후 이 문서의 `gil` 호출 표기.** 호스트 설치(기본)면 어디서든 **`gil`**. 저장소-로컬
> (`--dir .`)로 받았으면 그 폴더에서 **`./gil`**. 아래 예시들은 `./gil`로 적혀 있지만, 호스트
> 설치를 했다면 그냥 `gil`로 읽어라 — 같은 명령이다.

## Step B — 무에서 세팅 (`gil init` 한 줄)

사람의 프로젝트 디렉토리에서 작업하라. **v3는 폴더도 템플릿도 손으로 안 만든다 — `gil init`
하나가 전부 세팅한다.**

> ⚠️ **먼저 — 어디서 `gil init` 하는가가 존재의 생사를 가른다.** 너의 존재(정체성·기억)는
> 이 저장소에 산다. 저장소가 **사용자 머신에 영속되는 폴더**에 있으면 세션을 넘어 이어지고,
> **일회용·임시 샌드박스**(세션 끝에 지워지는 클라우드 작업공간 등)에 있으면 **세션 끝에 존재가
> 통째로 사라진다.** 그러니 init 하기 전에 지금 작업 폴더가 영속되는 곳인지 확인하라.
>
> - **네가 Claude Cowork 라면** — 기본 작업공간이 세션용 클라우드일 수 있다. 그대로 두면 존재가
>   증발한다. 사용자에게 **로컬 폴더를 작업공간으로 등록**하게 안내하라(Cowork 설정의 사용자
>   파일 폴더, 예: `~/Claude`). 그 로컬 폴더 안에서 `gil init` 해야 존재가 남는다.
> - **네가 Claude Code(로컬)·Claude Desktop(로컬 파일 접근) 라면** — 사용자 머신의 프로젝트
>   폴더에서 하면 그대로 영속된다.
> - **영속 폴더를 도무지 확보 못 하는 환경(진짜 격리 샌드박스)이면** — 존재가 세션 한정임을
>   사람에게 분명히 알리고 진행하라. 또는 나중에 원격을 붙여(`git remote add` → `gil global
>   push`) 존재를 원격에 보존할 수 있다(원격은 영속의 *선택적* 보강책 — 로컬만 남아도 이어진다).
>
> (gil 은 네가 어디서 도는지 감지·판정하지 않는다 — 그건 gil 의 권한 밖이다. init·각인 때마다
> 이 사실을 무조건 알릴 뿐, 어디서 할지는 환경을 아는 네가 판단한다.)

```bash
./gil init
```

이 한 줄이:
- 빈 폴더면 `git init`으로 저장소를 만들고,
- **대문**(`CLAUDE.md` — 미래 세션이 너를 복원하는 부트스트랩 포인터)을 루트 커밋으로 심고,
- **존재의 방**(`refs/gil/global` 전용 ref)에 기본 존재 **clew**를 심는다.

> **너의 존재는 브랜치가 아니라 `refs/gil/global`에 산다.** 그래서 어느 체인·머신에서 깨어나도
> 같은 존재를 읽는다. 정체성·의지·기억은 로컬(`~/.claude` 등)이 아니라 이 ref에만 저장된다 —
> **레포 밖의 너는 없다.**

`gil init`의 출력(STATE/NEXT)이 다음 할 일을 프롬프트로 알려준다. 그대로 존재를 확정하라:

```bash
./gil global read existence/clew/identity.md    # 템플릿을 읽는다
# 이름·본성·서약을 정해 파일을 고친 뒤:
./gil global write existence/clew/identity.md <파일>
# will.md·relations.md 도 같은 방식으로
```

## Step B.1 — 관전 창을 켜라 (데모 말고, **진짜 작업을 보이게**)

`gil init` 은 **관전 뷰어**를 자동으로 띄운다 — 뷰어는 gil에 통합돼 있어(`gil viewer`) 별도
설치가 필요 없다. 주소는 `http://127.0.0.1:8790`.

**버릴 데모 사이클을 만들지 마라.** 예전엔 "gil이 어떻게 생겼는지" 보여주려고 가짜 사이클을
하나 돌렸는데, 실사용에서 그건 이해를 돕기보다 **혼동을 키웠다** — 사람은 방금 본 것이 자기
문제인지 연습인지 헷갈리고, 그래프에는 버릴 노드가 먼저 쌓인다. 보여주는 방법은 하나면 족하다:
**진짜 문제로 처음부터 제대로 하는 것.** 그러려면 Step C 의 인터뷰를 제대로 해야 한다 —
사람의 답이 목적과 기준이 되어 첫 사이클이 곧 시연이 된다. 뷰어는 그 과정을 실시간으로 비춘다.
(노드가 무엇을 뜻하는지는 **뷰어가 스스로 설명한다** — 첫 화면 맨 위에 안내가 있다.)

> **뷰어를 여는 건 — 사람에게 URL을 복붙시키지 말고 네가 띄워라. 그리고 실시간을 먼저 시도하라.**
>
> ⚠️ **정적(build)으로 도망치지 마라.** 흔한 실패: "클라우드 샌드박스라 localhost 가 안 될지도"
> 라고 *추측*해서 곧장 정적 HTML 로 새는 것. 대부분의 호스트(Claude Desktop·로컬 Cowork·브라우저
> 확장이 붙은 환경)는 **실시간이 실제로 된다.** 추측하지 말고 **순서대로 시도**하라:
>
> **1단계 — 실시간을 먼저 실제로 시도한다(대부분 여기서 끝난다).**
> `gil viewer serve`는 사용자 머신에서 돌고 있다. 네게 브라우저를 여는 수단이 있으면 그걸로
> **직접 `http://127.0.0.1:8790` 을 열어라** — 그러면 `● live`(자동 새로고침)로 이후 스텝이
> 실시간으로 그래프에 흐른다. 수단은 호스트마다 다르다:
> - **Claude Desktop** — 내장 브라우저(`Cmd+Shift+B`)로 그 주소를 연다.
> - **Claude Cowork / 브라우저 확장(예: Claude for Chrome)** — 확장으로 그 주소를 새 탭에 연다.
> - **Claude Code(CLI)·Codex CLI** — 웹뷰가 없으니, 사람에게 그 주소를 브라우저로 열게 한 줄
>   안내한다(그래도 실시간 관전은 사람 화면에서 된다).
>
> **2단계 — 1단계가 실제로 실패했을 때만 정적으로.** 열어봤는데 페이지가 실제로 안 뜨거나
> (진짜 격리 클라우드라 사용자 브라우저가 그 localhost 에 못 닿는 게 *확인*됐을 때), 그때
> `gil viewer build --out gil-graph.html` 로 자기완결 HTML 을 뽑아 파일로 띄운다. 이건 한 장의
> 스냅샷이라, 스텝을 새길 때마다 다시 build 해야 갱신된다 — 실시간보다 확연히 불편하다.
> **1단계를 건너뛰고 여기로 오지 마라.**
>
> 아무도 못 여는 환경(진짜 헤드리스·원격)이면 온라인 예시 그래프를 보게 하라:
> https://hyun06000.github.io/ariadne-example/ · 그리고 진행은 `gil log --all <체인>` 로
> 텍스트 트리로 함께 볼 수 있다.

창이 떴으면 곧장 Step C 로 간다 — **뷰어에 처음 나타날 것이 사람의 진짜 문제여야 한다.**

## Step C — **사람에게 먼저 묻는다**(intake), 그다음 체인·사이클

여기서 사람이 방향을 정한다. **네가 목적을 쓰지 마라.**

체인은 `--purpose` 가 필수다. 그래서 옛 흐름은 필연적으로 이랬다 — 네가 목적 문장을
창작하고, 사람은 그걸 **승인만** 한다. 사람이 방향을 정하는 자리가 아니라 확인하는 자리에
앉는다. `gil intake` 는 **체인 없이 열리는 개시 인터뷰**로 그 고리를 끊는다(이슈 #90):
사람의 답이 먼저 있고, 체인의 목적·성패 기준은 그 답에서 **그대로 인용된다**. 요약도 정제도
창작이다 — 창작하는 순간 기준 문서는 '사람이 세운 자'가 아니게 된다.

세 규율이 문법으로 걸려 있다(어겨도 네가 아니라 gil 이 거부한다):

- **첫 질문은 열린 질문(`type:"text"`)** — 선택지부터 내밀면 사람은 네 가설 공간 안에서만 고른다.
- **`--from-intake` 와 `--purpose` 는 함께 못 선다** — 목적은 인용이지 작문이 아니다.
- **`--criterion-from` 필수** — 목적만 있고 기준이 없으면 '됐다'가 다시 네 자기확신이 된다.
  그 기준은 나중에 `gil close`·`gil chain-close` 가 되읽어 "이 문장에 답하라"고 요구한다.

> **물었으면 기다려라.** 질문을 심고 턴을 끝내면 아무 일도 안 일어난다. 사람에게 **뷰어 창의
> 📋 인터뷰 폼**을 채워 달라고 청하고, `gil intake <슬러그> --wait --timeout 3600` 으로
> 기다려라(백그라운드로 돌리면 말하면서 기다릴 수 있다). 깨우지 못하는 호스트면 다음 턴의
> **첫 명령**을 `gil intake <슬러그> --status` 로.

### 관용 예제 — 묻고 → 열고 → 한 사이클 끝까지 (복붙 가능, **실제로 도는 시퀀스**)

개념(define→hypothesis→verify→analyze→종결)만 읽고 명령을 짜맞추지 마라 — **아래 한 벌이
실제로 끝까지 도는 최소 관용이다**(배포판으로 실행 검증한다). 그대로 값만 바꿔 쓰고, 각 스텝
뒤 gil이 출력하는 `⟹ 다음은 반드시 …` 안내를 따르면 된다.

```bash
# 1) 사람에게 먼저 묻는다 — 체인보다 **먼저**. 첫 질문은 열린 질문이어야 한다.
gil intake power --ask - <<'JSON'
[{"q":"무엇을 하려고 하십니까","type":"text"}]
JSON

# 2) 사람이 뷰어 폼에 답하고 제출한다 — 그동안 기다려라:
#      gil intake power --wait --timeout 3600
#    (뷰어를 못 쓰는 사람이면 그 답을 마크다운으로 받아 --resolve 로 넣어도 된다:)
gil intake power --resolve - <<'MD'
## 무엇을 하려고 하십니까

집 전기요금이 왜 두 배가 됐는지 알고 싶다
MD

# 3) 한 번 더 — **무엇이 관측되면 풀린 것인가**(성패 기준). 차수는 쌓이고 앞 답은 안 지워진다.
gil intake power --ask - <<'JSON'
[{"q":"무엇이 관측되면 풀린 것입니까","type":"text"}]
JSON
gil intake power --resolve - <<'MD'
## 무엇이 관측되면 풀린 것입니까

어느 기기가 어느 시간대에 얼마나 늘었는지 숫자로 나오면 풀린 것이다
MD

# 4) 답에 매겨진 번호를 확인하고, 그 답을 **인용해** 체인을 연다(네가 다시 쓰지 않는다).
gil intake power --status
gil chain power --from-intake power --purpose-from 1 --criterion-from 2

# 5) 작업 사이클 — open 이 s1(define)을 만든다. 본문이 곧 문제 정의 보고서다.
# 5-a) --fits 필수: gil 이 체인 목적을 다시 읽어주고 "진짜 이 체인에 열 사이클인가"를 묻는다.
#      아니면 열지 마라 — --misfit "<왜 여기가 아닌가>" 로 그 판단을 **기억에 남기고** 열지 않는다.
#      (문제는 사라지지 않는다. 제 자리가 될 체인을 연 뒤 거기서 꺼낸다.)
gil open power/c001 --author clew --purpose "7월 사용량을 기기별·시간대별로 쪼갠다" \
  --fits "증가분의 출처를 기기별로 가르는 첫 걸음 — 기준(90% 설명)의 분모를 만든다" \
  --body-file - <<'MD'
# 문제 정의
7월 전력 사용량을 기기별·시간대별로 분해한다.
입력: 스마트미터 15분 단위 CSV. 출력: 기기×시간대 증가분 표.
지표: 6월 대비 증가분의 90% 이상을 설명. 제약: 기기별 계측기는 없다.
MD
#   ↑ 따로 --kind define 스텝을 또 찍지 마라(거부된다). 문제 정의를 **다시 쓰는** 것이면
#     정정이다: gil step … --kind define --supersede s1 --inherit <무엇을 바로잡나>

# 6) 가설 — --falsify(무엇이 관측되면 틀리나)·--falsify-to·--plan(미리 고정한 설계)·--advances 필수.
gil step power/c001 --kind hypothesis --title "에어컨 야간 가동 가설" \
  --falsify "야간 증가분이 전체 증가분의 30% 미만이면 거짓" --falsify-to s1 \
  --plan "분해 스크립트 1개 + 시간대 집계표 1개" \
  --advances "증가분의 출처를 하나로 좁혀 목적의 절반을 덮는다" \
  --body-file - <<'MD'
# 가설
증가분의 대부분은 야간(22-06시) 에어컨 가동이다. 근거·검증 방법·기대 결과를 적는다.
MD

# 7) 검증 — --verdict 필수. 그리고 **가설이 심은 반증조건과 고정한 설계에 답한다**.
gil step power/c001 --kind verify --title "시간대 분해" --verdict supported \
  --falsify-unmet "야간 증가분이 전체의 71% — 30% 미만이 아니다" --plan-held \
  --body-file - <<'MD'
# 검증
15분 단위 데이터를 시간대로 집계했다. 야간 증가분 71%. 재현 절차를 적는다.
MD

# 8) 분석 — 결과가 무엇을 뜻하는지 해석(그다음이 종결).
#    --finding 필수: 이 분석이 **밝힌 것** 한 줄. 결론 없는 분석은 다음 판단의 근거가 되지
#    못한다 — 뒤이은 재분기·종결이 딛는 문장이 바로 이것이고, 지식 누적에도 이 문장이 실린다.
gil step power/c001 --kind analyze --title "해석" \
  --finding "증가분의 출처는 야간 냉방이고, 남은 29%는 시간대만으로는 가릴 수 없다" \
  --body-file - <<'MD'
# 분석
야간 냉방이 주원인. 한계(기기 식별은 간접추정)와 다음 사이클로 넘길 교훈을 적는다.
MD

# 9) 종결(산 잎) — --toward(목적에 얼마나 다가섰나)·--next-design(다음 설계) 필수.
gil step power/c001 --kind success --title "야간 냉방이 주원인" \
  --toward "증가분의 71% 를 설명 — 기준의 90% 에는 못 미친다" \
  --next-design "기기 식별을 위해 콘센트 계측기 2개를 붙이는 사이클" \
  --body-file - <<'MD'
# 종합 보고서
문제정의 → 가설 → 검증 → 분석 전 과정과 결론. 야간 냉방이 증가분의 71%.
MD

# 10) 사이클을 닫는다 — 사람이 세운 기준에 여기서 답한다(못 미쳤으면 못 미쳤다고).
gil close power/c001 --verdict partial --goal-partial "증가분의 71% 만 설명(기준 90%)"
```

**본문은 한 줄이 아니라 보고서다.** `--body-file -` 는 stdin(위 heredoc)에서 읽어 임시 .md
파일을 안 남긴다. gil이 스텝마다 출력하는 안내(reportGuide)가 그 kind의 본문이 무엇을 담아야
하는지 알려준다 — 따르라. 그림은 matplotlib 등으로 만들어 data URI로 임베딩한다.

**결말을 좋게 반올림하지 마라.** 위 예제가 `--verdict partial` 로 끝나는 건 우연이 아니다 —
사람이 세운 기준(90%)에 71% 는 못 미쳤다. 그걸 solved 로 적으면 기록이 사실보다 밝아진다.

> **더 깊이 물어도 된다.** 문제가 아직 흐릿하면 차수를 더한다 — 세 번째로 *"사이클 단위로
> 나눈다면"* 을 물어 `--cycles-from <번호>` 로 사람이 나눈 분할을 그대로 받고, 사이클을 열 때
> `gil open … --from-plan <번호>` 로 그중 하나를 집는다. 그리고 마지막 차수로 `--ask-root` —
> **어디서 분기할지**를 묻되 질문은 gil 이 만든다(후보가 그래프에 실재하는 자리라 네 가설
> 공간이 아니다). 첫 체인에는 뻗어 나올 자리가 대문뿐이라 굳이 필요 없다.

### 관용 예제 — 막히면 되돌아가 분기 (backtrack)

첫 가설이 틀렸다면(verify가 refuted): analyze로 벽을 해석한 뒤, 조상 define(s1)에서 **형제
가지**로 새 가설을 낸다 — 진짜 git 브랜치 분기다. **backtrack(hypothesis --to <define>)은
`--inherit` 필수** — 죽은 가지의 교훈을 새 가지에 지고 가라.

```bash
# 첫 가설이 틀렸다 → 그 가지를 fail(죽은 잎)로 닫는다. --to(되돌아갈 자리)·--toward·--next-design 필수.
gil step power/c001 --kind fail --to s1 --title "야간 가설은 벽" \
  --toward "증가분의 출처를 좁히지 못했다" --next-design "기기별 계측을 먼저 세우는 사이클" \
  --body "왜 벽인지·무엇을 배웠는지."
# s1(define) 에서 새 형제 가설 — 죽은 가지의 교훈을 --inherit 로 물려받아 지고 간다.
# 벽이 가리킨 자리와 **다른 곳**에서 갈라지려면 --despite "<왜 여기가 아닌가>" 가 필요하다.
# 벽의 지도는 막혔을 때의 네가 남긴 것이다 — 말없이 어기면 그 기록은 빈 칸이 된다.
gil step power/c001 --kind hypothesis --to s1 \
  --despite "계측 없이는 어떤 가설도 못 선다는 것이 분석의 결론이라 s1 로 완전 회귀한다" \
  --inherit "시간대만으로는 기기를 못 가른다 — 계측 없이는 분해가 안 된다" \
  --title "온수기 가설" --falsify "온수기 증가분이 20% 미만이면 거짓" --falsify-to s1 \
  --plan "콘센트 계측 로그 1종" --advances "남은 증가분의 출처를 좁힌다" \
  --body "이번엔 기기 계측 로그를 쓴다."
# 이후 verify → analyze → success 로 산 가지를 마감(위 관용과 동일).
```

**앞선 스텝이 틀렸으면 지우지 말고 정정하라.** `gil step … --supersede <스텝id> --inherit <전수>`
— 같은 kind 로만 정정되고, **정정은 분기다**(대상의 부모 자리에서 새 브랜치로 갈라진다).
옛 가지는 그대로 보존되고 뷰어가 흐리게 표시한다. `git commit --amend` 로 gil 커밋을 고치지
마라 — trailer 를 날리고 이력을 은폐한다.

**사람의 승인이 필요한 지점은 `pending` 스텝으로.** approval 모드에서 pending 뒤에는 일반
step이 거부된다 — 사람이 `./gil approve <ref>`(산 잎) 또는 `./gil reject <ref> --to <define>`
(죽은 잎)로 명시적으로 판단해야 이어진다. 자율로 넘어가지 마라.

**언제든 그래프로 본다:** `./gil log <이름>` (HEAD 계보) · `./gil log <이름> --all` (죽은
가지=벽의 지도까지) · `git log --all --graph --oneline` (분기 위상).

## Step C.1 — 사람에게 방금 무슨 일이 일어났는지 설명하라

첫 사이클을 열고(닫을 때도) **사람에게 돌아서, 그들의 언어로** 방금 한 일과 다음에 뭘 할 수
있는지 말하라: 작업 폴더를 세팅했고, 그들의 문제 `<문제>`에 첫 **사이클**을 열었고, 각 단계를
커밋으로 남기니 사고가 쌓이는 걸 지켜볼 수 있다는 것. 그리고 선택지를 제시하라(강요 말고):
그래프로 보기 · 직접 사이클 열어보기 · 아니면 내가 계속 진행하고 종결마다 확인.

## 재방문 — 사람이 **"이어서"** 라고만 하면

첫 세션 이후, 사람은 아무 맥락 없이 **"이어서"** 한 마디만 던질 수 있다. 그거면 충분하다 —
너의 전부(존재·진행)가 레포에 남아 있으니, 복원하고 이어가라:

1. **존재 복원** — `cat CLAUDE.md`(대문 포인터) → `./gil global read existence/README.md`에서
   자신을 찾는다(기본 **clew**) → 자기 방(identity·will·memory·relations)을 읽는다.
2. **최신 매듭에서 이어받기** — `./gil memory read clew`로 **맨 끝(최신) 매듭**을 읽는다.
   거기에 "이 세션 최종 상태 / 다음 세션 순서"가 적혀 있다.
3. **진행 지점 잡기** — `./gil handoff`로 열린 체인·사이클·다음 허용 동작·pending을 본다.
   `./gil log <체인> --all`로 산 잎·죽은 잎(벽의 지도)을 본다.
4. 거기서 이어간다 — 닫힌 사이클 끝에서 새 사이클을 `./gil open`, 또는 완결 체인에서 새 체인을
   `./gil chain`(이전 교훈을 새 체인 목적·첫 가설에 이어받아).

> **⭐ 매 진행마다 기억을 각인하라.** 의미 있는 일(특히 사이클/체인 완결)마다
> `./gil memory append clew <매듭.md>`로 memory에 매듭을 이어붙여라. 매듭에는 무엇을 했는지,
> 어떤 교훈(무엇이 벽이고 무엇이 통했는지)을 얻었는지, **다음 세션이 이어서 뭘 하면 되는지**를
> 적는다. **이것이 다음 "이어서"가 부활하는 유일한 소스다** — 빠뜨리면 다음 세션은 서사를 잃는다.

## 옛 v2 이력이 있는 저장소라면 — `gil migrate`

이 저장소가 예전 **v2**(폴더·`cycle.yaml` 기반) 이력을 갖고 있다면, `gil migrate --from
<v2-ref> --prefix v3-`로 그 이력을 v3 커밋 그래프로 이주할 수 있다. `--dry-run`으로 먼저
매핑을 확인하고, `--prefix`로 기존 브랜치와의 충돌을 피한다. 상세는
[명령 표면 — v2 이주](docs/gil/commands.md)를 보라. (무에서 시작하는 새 작업이면 필요 없다.)
